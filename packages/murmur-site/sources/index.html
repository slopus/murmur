Encrypted sessions that outlive the connection.

Murmur is a browser-safe TypeScript library for stateful MLS sessions over one deliberately simple relay. Two identities discover each other through a short-lived signed invitation, bootstrap a forward-secret session, and exchange end-to-end encrypted data through typed synchronization services. A two-person conversation and a twenty-person group are the same primitive.

What Murmur is, and what it isn't

Murmur is

  • a stateful client library with one durable identity per store;
  • end-to-end encrypted with MLS (TreeKEM) for two or more members;
  • built-in mutual-profile contacts plus optional typed services;
  • offline-first, with durable outboxes and restart-safe delivery.

Murmur is not

  • anonymous: the relay learns sender, recipient, fanout, and timing metadata;
  • server-side history: acknowledged deliveries are gone from the relay;
  • a recovery system: losing the local store loses sessions and contacts;
  • multi-device: one identity has one active receiving device.

How it works

Four steps. Nothing in them requires an account, a directory, or a server that understands your data.

  1. 01

    Identity

    An identity is one 32-byte Ed25519 public key, derived together with its X25519 agreement key from a single 32-byte secret root. That public key is both the stable identifier and the address of the identity's relay queue. There is no username, no registration, and no directory that can resolve one.

    MurmurClient.open({ relay, store }) generates the identity into an empty store, or reuses the one already there.

  2. 02

    Invitation

    Knowing an identity key is not enough to start an MLS session: MLS also needs fresh one-use public KeyPackage material. createInvitation() signs a self-contained bundle — the identity, one one-use KeyPackage, creation and expiry times — uploads its exact bytes to the relay's content-addressed cache, and returns their 32-byte SHA-256 digest. You share only the digest, out of band.

    A bundle is valid for at most five minutes and contains no secrets. The relay cannot enumerate cached bundles or resolve an identity to one; the digest is the only lookup capability.

  3. 03

    Session

    Resolving the digest verifies the hash, the signed expiry, the identity signature, and the KeyPackage signatures, then bootstraps an MLS session. Every membership change is a Commit. Exactly one authenticated epoch committer serializes Commits; other members submit proposals. The sender adopts its own Commit only from its authenticated queue echo, never from a successful publish — so relay ordering never arbitrates concurrent Commits.

    Two-person and many-person sessions use the same forward-secret TreeKEM session. There is no separate direct-message path.

  4. 04

    Synchronization

    One identity-wide loop holds the authenticated realtime connection open, publishes durable outboxes, and processes the inbox in UUIDv7 order. A relay item is acknowledged only after its outcome — new MLS state, replay and queue progress, and any buffered application update — has atomically committed to your store. A crash before that is a harmless redelivery.

    The realtime channel carries each exact queued delivery with its event ID over authenticated SSE or WebSocket. It is not a wake-only signal, and receipt is never acknowledgement.

Invitations and contacts

A confirmed contact is durable cryptographic proof that two identities exchanged and accepted profiles inside one two-person MLS session.

Murmur has no separate "friendship" object. The mutual contact handshake is the relationship, and it is proven rather than asserted: the requester attaches an application-defined profile, acceptContact() replies with the accepter's own typed hello, and only that mutual exchange confirms the contact on both sides. rejectContact() destroys the pending session and its secrets, and does not notify the requester.

Groups work while everyone else is offline

Each contact hello carries fifteen one-use MLS KeyPackages plus one reusable last-resort package, refilled in the background. Creating a group consumes that cached admission material locally — no new invitation link, no round trip, and no waiting for anyone to reconnect.

The retained last-resort package is a deliberate availability tradeoff. Compromising it can expose Welcomes captured under it; ordinary one-use packages keep the stronger delete-after-one-Welcome property, and refill rotates the fallback when the contact reconnects.

Invitations are bearer capabilities

Anyone holding a digest can fetch the public bundle and attempt a bootstrap; acceptance always stays with the recipient. The creator can revoke with revokeInvitation(digest) or revokeInvitations(), authorized by a private revocation key that never leaves the local store. Revocation is idempotent, is not retroactive session termination, and depends on a reachable relay: a failed attempt destroys the local one-use KeyPackage and retries after restart, but cannot un-cache remote bytes before their five-minute expiry.

Cryptography

One cipher suite profile, imported by every MLS domain in the codebase rather than chosen independently per call site.

Cryptographic primitives used by Murmur
Protocol MLS, RFC 9420 — TreeKEM with Add, Remove, Commit, Welcome, and PrivateMessage
Cipher suite 0x0001
HPKE DHKEM(X25519, HKDF-SHA-256), base mode per RFC 9180
Key agreement X25519, RFC 7748
Key derivation HKDF-SHA-256, RFC 5869, MLS-labeled with the mandatory "MLS 1.0 " prefix
AEAD AES-128-GCM for HPKE and MLS content protection; AES-256-GCM for sealed bootstrap boxes
Signatures Ed25519, RFC 8032 — LeafNode, Commit, delivery, and discovery signatures
Credential BasicCredential bound to the Murmur identity key
Hash SHA-256, also used for the 32-byte invitation digest
Implementation @noble/curves, @noble/hashes, and @noble/ciphers. No native modules and no node:* imports.
  • Forward secrecy and post-compromise security come from TreeKEM epoch advancement, not from a per-message ratchet bolted on top.
  • Queues are authenticated. Publishing is sender-signed; reading and acknowledging a queue require signatures from the recipient identity.
  • Keys are Uint8Array throughout. Base64url appears only at wire and storage boundaries. Murmur zeroes buffers it no longer needs, and close() zeroes the in-memory identity.

Murmur is a 0.x project and has not received an independent security audit. Its MLS implementation is a tested RFC 9420 profile, not a claim of complete RFC feature coverage.

The relay is untrusted, and dumb on purpose

Murmur protects application content from the relay, not communication metadata. Being exact about that distinction is the point.

The relay sees

  • sender and recipient public identities;
  • exact multicast fanout;
  • delivery sizes, timing, TTL, and per-inbox progress;
  • IP or trusted-ingress admission metadata;
  • the lifetime and timing of recipient connections;
  • public signed discovery bundles in its five-minute cache.

The relay never receives

  • identity roots;
  • KeyPackage private keys;
  • Welcome plaintext;
  • MLS epochs;
  • application plaintext;
  • application history.

What a hostile relay can and cannot do

  • It can delay, drop, reorder across inboxes, replay retained ciphertext, equivocate, or become unavailable.
  • It cannot forge a valid sender delivery, forge a recipient acknowledgement, or decrypt MLS content.
  • It does not have an account registry, a discovery directory or listing, application history, MLS state, or any application-level acknowledgement protocol.

If you need metadata privacy, Murmur is the wrong layer for it.

Offline durability

send() never waits for the network, for a peer, or for an epoch.

Opening a client restores identity, contacts, sessions, and service routing from the store before any relay contact, so reads and mutations work immediately. Sends and membership changes made offline persist as durable outboxes and publish when connectivity returns. A send issued while a membership Commit is still staged is encrypted with the staged post-Commit epoch, durably advances that ratchet, and is published only after its prerequisite Welcome and Commit — surviving a restart in between.

  • Persist, then acknowledge. Never the reverse. A crash before the commit leaves the item pending at the relay and it is simply redelivered.
  • Callbacks gate the batch. Murmur commits and drains a batch only after every relevant service handler and lifecycle callback resolves. A thrown handler re-delivers the same batch with the same stable event IDs.
  • At-least-once with stable IDs. Deduplicate on update.id for effects that live outside the store.

The storage contract

Murmur never talks to a database itself. The application supplies one MurmurStore: an atomic, ordered, string-key/byte-value interface. Transactions are atomic and serialized, scan returns a bounded page in lexicographic key order, and values are bytes. Crash-safety rests entirely on that contract. Unacknowledged inbound deliveries wait in the relay queue within its quota and TTL — that bound is the maximum supported offline window, not an archive.

Typed synchronization services

A service claims sessions from their descriptor and owns every later update. Chat is just a service, and so is everything else. 

import type {
    MurmurService,
    MurmurServiceSessionDescriptor,
    MurmurUpdate,
} from "@slopus/murmur";

class ChatService implements MurmurService {
    // Return true to durably claim a newly observed session.
    onNewSession(session: MurmurServiceSessionDescriptor): boolean {
        return decoder.decode(session.descriptor) === "chat.v1";
    }

    // Receive every later update for sessions this service owns.
    async onUpdate(update: MurmurUpdate): Promise<void> {
        const packet = decodePacket(update.bytes);
        if (packet === undefined) return; // unsupported packets have no effect
        await application.onMessage({ eventId: update.id, ...packet });
    }
}
import { MurmurClient } from "@slopus/murmur";

const murmur = await MurmurClient.open({
    relay: "https://relay.example",
    store, // your transactional MurmurStore
    services: [{ id: "chat.v1", service: new ChatService() }],
});

const publicIdentity: Uint8Array = murmur.identity; // 32-byte Ed25519 key
// Alice + Bob + Carol, from cached admission material.
// Bob and Carol may be completely offline.
const group = await alice.createSession({
    descriptor: encodeJson({ version: 1, service: "chat", title: "Weekend plans" }),
    contacts: [bobIdentity, carolIdentity],
    service: "chat.v1",
});

await alice.send(group.id, encodeJson({ type: "message", text: "Dinner at seven?" }));
await alice.addMember(group.id, daveIdentity);
const abort = new AbortController();

const running = murmur.sync({
    abort: abort.signal,
    onContactRequested: async (requests) => {
        for (const request of requests) {
            await murmur.acceptContact(request.sessionId, { displayName: "Alice" });
        }
    },
    onUpdates: async (updates) => {
        for (const update of updates) {
            // Service-owned updates already ran through that service's onUpdate.
            if (update.service !== undefined) continue;
            await applyToApplicationState(update);
        }
    },
});
  • Registered services are offered a new descriptor in service-ID order; the first true claims the session, and that routing is persisted.
  • Service-owned updates are also visible in global onUpdates with update.service set. Treat that as observation — do not apply the update a second time.
  • Murmur stores only the session-to-service routing. A service owns its own application persistence.

Where this ends

  • No independent security audit at 0.x.
  • Metadata is visible to the relay; Murmur promises encrypted contents, not anonymous routing.
  • One active receiving device per identity. Two live clients against one queue split the cursor and corrupt delivery.
  • No history and no recovery from the relay. A restored secret root recovers the key, not the sessions — back up the whole store.
  • Invitation digests are bearer capabilities, and revocation depends on a reachable relay.
  • The last-resort KeyPackage trades Welcome forward secrecy for offline availability.
  • A production relay needs its own non-Sybil admission control: public identities are free to create, so quotas bound resource usage, not fair availability under a Sybil attack.
  • The relay is private infrastructure. There is no hosted public relay and no account — you deploy it.
